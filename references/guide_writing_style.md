# 指导书写作规范（阶段 4）

## 读者画像

一般是本科生，会 Python、会装包，但对该领域和工程细节不熟。他会**照着指导书一行行敲命令**，遇到和指导书不一样的输出就会慌。所以指导书要做到：命令可复制、输出可对照、出错有去处。

## 整体结构

1. 头部信息：项目链接、本地路径、读者、路线、理论深度
2. 目录（带锚点）
3. "写在前面"：30 秒项目概述 + 数据流图、标记说明、准备好的脚本清单、所有命令在哪个目录执行、卡住了怎么求助
4. 阶段 0 环境（第一小节放"**文档 vs 代码差异表**"）
5. 阶段 1 领域知识（够用就行）
6. 阶段 2 数据探索 → 阶段 3 核心变换/算法 → 阶段 4 模型 → 阶段 5 训练 → 阶段 6 评估
7. 辅线（GUI/Notebook 等）
8. 对比实验（给出你已经跑出的参考结果 + 请学生完成的实验表）
9. 总结与拓展（报告模板、自查清单、进阶方向）
10. 附录 A 常见报错速查表；附录 B 资源与论文；思考题答案（`<details>` 折叠）

阶段的划分按项目实际情况调整，不必死守 0~9，但顺序要遵循"环境 → 懂领域 → 看数据 → 懂算法 → 懂模型 → 训练 → 评估 → 实验 → 拓展"。

## 每个阶段的六段式

```markdown
## 阶段 N · 标题

🎯 **目标**：一句话。
⏱ 约 X 天

### N.1 原理（📖）
- 先给一句话定义，再给类比，再给**手算数值例子**（带表格更好）。
- 讲清"为什么需要它"和"它在代码哪里"（给出文件路径和函数名）。

### N.2 动手（💻）
```bat
python my_repro\stepN_xxx.py
```
实测输出（摘录关键行，并用 ← 注释解释）：
```
...
```

### N.3 注意点（⚠️）
- 写成"现象 → 原因 → 解决"，并告诉学生在日志里怎么自己发现它。

✅ **验收**：可检查的具体标准（数值范围、文件存在、能口述某个结论）。

🤔 **思考题 N**：一个能引发思考的问题（答案放文末）。
```

## 写作要点

- **数字要有出处**。"预期输出"必须是你实测的；随机性带来的波动要给出范围（如 ±0.3 dB）。
- **理论深度跟着用户的选择走**：
  - 只要会用：定义 + 类比 + 数值例子 + 代码位置，不推导；
  - 直觉 + 关键公式：再加核心公式和每个符号的含义；
  - 推导：再加推导过程与参考教材章节。
- **用学生熟悉的东西类比**（例如：小波 ↔ JPEG2000，自编码器 ↔ "用 256 个数描述一张图"，三阶段训练 ↔ "编词典 → 学查词典 → 实战磨合"）。
- **绕过 bug 的代码要贴出来并解释**，同时告诉学生如果要给原作者提 PR 该改哪里。
- **敢于写"和 README 不一致"**。如实报告实测结果与 README 的差异并分析原因，这往往是整本指导书最有价值的部分。
- **区分已验证和未验证**：比如 GUI 步骤是依据源码控件整理的，要明确标注。
- **平台细节**：用户是 Windows 就给 `bat` 命令和反斜杠路径；提醒 Anaconda Prompt、VS Code 解释器选择、控制台编码。
- **别让学生白跑长任务**：先 `--quick` 冒烟测试，再跑正式配置。
- 长度参考：一个中等规模仓库大约 800~1200 行 Markdown。宁可详尽，也不要让学生卡住。
